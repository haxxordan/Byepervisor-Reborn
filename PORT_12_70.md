# Firmware 12.70 port status

The 12.70 table in `include/offsets/12_70_candidate.h` is staged from the
unpublished EchoStretch ELF analyzed in
`/home/deep/src/ps5/testing/byepervisor-reborn-elf-analysis.md`. The table has
14 symbol and 21 gadget entries. Its order was checked against the 13.60
source table, and `PMAP_STORE`, `IDT_ARRAY`, and `COMMON_TSS` agree with public
kstuff-lite values after converting from the data base to the text base.
This is still a **candidate table**: most gadget bytes, the resume call site,
and the AP/HV offsets have not been independently verified on 12.70.

The regular `byepervisor_reborn.elf` exits early on 12.70, before modifying
kernel memory or installing a hook. The dedicated `preflight-1270.elf` is a
read-only diagnostic that has now passed on the launch-model console. Neither
ELF is a Linux loader.

## Confirmed on the launch-model 12.70 console

A bounded page-walk probe read `PMAP_STORE` successfully and derived a direct
map base of `0xffff825900000000`. The kernel text range contained eight sampled
2 MiB spans: six 2 MiB PDE leaves and two 4 KiB-table PDEs. That confirms the
upstream page loop's unconditional `find_pte()` descent would treat mapped
kernel text as a page table on this console. Commit `e65f5fa` makes the common
walker reject 1 GiB and 2 MiB leaves, skips `find_pte()` for large text PDEs,
and fixes the physical-address mask to bits 12–51. The corrected HV payload
has not been run on 12.70.

The original write wrapper ignored `kernel_copyin` errors, so the captured
panic log cannot prove which bad write succeeded. The old Discord ELF remains
unsafe to rerun.

The 12.70 preflight then completed with `PREF1270,1,end,ok`:

- `PMAP_STORE` yielded PML4 `0xffff8259195b4000`, CR3 `0x195b4000`, and
  direct-map base `0xffff825900000000`. Candidate `DMPML4I=260` and
  `DMPDPI=356` reconstruct that same base.
- The carrier VA `0xffff82593ffff000` resolves through a present 2 MiB PDE
  leaf (`0x000000003fe001e3`). Its PML4 entry has NX set before the loader's
  page-table changes. The corrected walk must stop at that PDE.
- The candidate cave's oracle, state, and scratch qwords were all zero. The
  existing `#DB` gate is present, selector `0x20`, interrupt-gate type `0xe`,
  and its handler falls inside the kernel image. Core 0 TSS RSP0 is canonical;
  IST6 is zero before any hook is installed.

These observations support the candidate **data** offsets and page layout.
They do not validate the resume call instruction, ROP gadgets, or AP-time HV
globals. The shared `kread`/`kwrite` wrappers now return SDK copy errors to
callers; single-value reads initialize their output to zero on failure. More
error handling is still needed around the full hook path.

## Read-only preflight

Build from this directory with the configured PS5 payload SDK:

```sh
make preflight-1270.elf
```

The preflight checks firmware and SDK kernel bases, reads the pmap fields,
compares candidate direct-map globals with the pmap-derived base, walks the
`0x3ffff000` physical carrier mapping without modifying it, and reads three
data-cave qwords plus the existing `#DB` gate and core-0 TSS fields. It reports
lines beginning `PREF1270,1,` and shows a short completion or stop
notification. It does not read execute-only kernel text, install a hook,
request rest mode, or write target page tables. Invalid kernel reads can still
panic a console, so it is a bounded diagnostic rather than a zero-risk test.

## Remaining gates before a full 12.70 attempt

1. Independently validate the candidate resume call site and reachable gadget
   instructions against 12.70 executable bytes. Their presence in an ELF table
   is not proof that they have the expected effects on this console.
2. Determine whether the 12.70 AP window has usable hypervisor heap/`pcpus`
   globals. The 11.60 port reports those globals were zero during its AP
   window and used guarded runtime VMCB discovery instead. Its fixed physical
   heap range must not be copied to 12.70 without measurement.
3. Resolve the immediate panic from the first AP diagnostic run before any
   further hook or resume test. Three bounded GPU DMA reads of executable
   12.70 kernel-text pages returned only `0xff`, including the live `#DB`
   handler page. This tested GPU path has not recovered instruction bytes. The
   one decrypted PUP kernel block saved so far does not expose a recognizable
   kernel header either.

## Intended post-resume milestone

The full payload changes the kernel text page permissions before rest mode,
then uses the resume/AP path to defeat the remaining HV protection. On a
successful return, `main.c` reads and notifies the first eight bytes of kernel
`.text`. A stable post-resume state should then allow a separate full kernel
dump and patching. The eight-byte notification alone demonstrates a readable
sample, not that a full dump has been completed or that Linux boots. Linux
loader and kernel support remain separate work.

`4e0c596c93ff4283589422bac5d0e2efb7780a37101bcf3c0554569d27d72991`)
printed `P1270DIAG,1,start`, `Installing hook...`, and
`install_resume_hook: setting hook target = 0xffffffffd63ddfb0 ...
set rsi=0xffff82593ffff000`, then the console kernel-panicked. It did not
print the ready marker or enter rest mode. The displayed markers put the failure
after the carrier setup and inside `install_resume_hook()` or its immediate
caller. They do not distinguish `kh_install()` from `kh_trigger()`: there is no
stage marker between those operations, and the klogsrv capture did not retain
the payload markers. Candidate hook gadgets and the execution of the `#DB`
chain remain unverified. **Do not rerun this ELF.**

The next step is an offline audit of the 12.70 hook gadget bytes and chain,
followed by a separately staged diagnostic only if it can narrow the failure
without repeating the same immediate trap. A successful AP result has not been
observed, so the kernel is not yet readable through this route.

The first offline check found two suspicious candidate gadget addresses.
`POP_RDI` is at text-relative `0xD65548`, which is `0x15548` beyond the SDK's
observed `KERNEL_ADDRESS_DATA_BASE` gap (`0xD50000`). `CLD` is at `0x1226933`,
even farther beyond it. The arm chain uses `POP_RDI` immediately after its
first `POP_RAX`.
The 11.60 port's hook staging messages distinguish `kh_install()` from
`kh_trigger()`, but this 12.70 run did not include those messages.

`gadget-page-probe-1270.elf` is a separate read-only payload for that narrow
question. It walks the kernel pmap for the candidate pivot, `POP_RAX`,
`POP_RDI`, `DBREG_RESUME`, `IRETQ`, `CLD`, and resume call site. It reports each
leaf mapping and effective NX status under `GPG1270,1,` and a short summary
notification. It reads page-table entries only; it does not read execute-only
kernel bytes, write kernel memory, install a hook, or enter rest mode. The
candidate pmap and direct-map addresses are checked before walking, but an
invalid kernel read can still cause a panic.

The probe completed on the launch-model 12.70 console with `nx_targets=2/7`.
The `POP_RDI` 4 KiB PTE was `0x800000000e3d5121` (NX set), and the `CLD`
2 MiB PDE was `0x800000000e8001a1` (NX set). The pivot, `POP_RAX`,
`DBREG_RESUME`, `IRETQ`, and resume call target were present with NX clear.
This confirms the two candidate ROP addresses cannot execute under the
observed mappings. It strongly explains the immediate hook panic, but the
capture does not prove the exact faulting instruction or validate the bytes
at the other five addresses. A rebuilt AP diagnostic now exits before kernel
changes while either known-NX candidate offset remains in the table; the
previous 177-byte diagnostic ELF (SHA-256 beginning `4e0c596c`) remains unsafe
to rerun. The guarded rebuild has SHA-256
`82ee82c9da8cf0bc4798f1acdf91d201082bf975e50965e2ce87bb796b055271`.
This guard does not make the hook viable: replacement gadget instruction bytes
and effects are still unverified.

## Route to verified 12.70 kernel bytes

No independently published replacement for the two NX gadget offsets was found
in the sources checked. The 13.60 GPU DMA research in
`/home/deep/src/ps5/testing/hv-bypass-1360-reference` describes a method for
reading execute-only kernel text through a GPU mapping, but its tested GPU VM
layout and DMA behavior are 13.60 results. They are not 12.70 offsets or a
ready-to-run 12.70 dump payload.

The first port gate is a **read-only GPU VM inventory**. The public 12.70 IDT
offset is `KERNEL_ADDRESS_DATA_BASE + 0x2E88300`; the 13.60 research places
the 12.70 `gvmspace` array `0x9D90` bytes before it, at data offset
`0x2E7E570`. `gpuvm-preflight-1270.elf` checks those two calculations, reads
the already-tested IDT gate, then reads only the first `0x40` bytes of each of
16 proposed `0x100`-byte GPU VM entries. It logs raw state, bounds, and page
directory fields as `GVM1270,1,` records. It does not open `/dev/gc`, submit a
GPU command, modify a page table, read execute-only text, or install a hook.
The inventory ran on the launch-model 12.70 console. All 16 rows were
readable, with five non-free states (0, 2, 3, 4, 5). The other 11 rows had
state `0x20`. The 16 page-directory pointers were canonical and aligned;
their underlying physical addresses ran from `0x15ea8000` through
`0x15ee4000` in `0x4000` steps. This supports the proposed array location
and field layout, though it does not identify a process VMID or validate a
GPU mapping.

The mapping probe, `gpuvm-map-probe-1270.elf`, opens `/dev/gc`, allocates and
maps one 2 MiB garlic buffer through the system APIs, and walks only the
three GPU page-table levels indexed by that buffer's virtual address for
each populated VMID. It bounds physical reads to 16 GiB, logs the raw
entries and matching VMIDs as `GVMMAP1270,1,` records, then unmaps, releases,
and closes the device. It sends no GPU ioctl, DMA request, or page-table
write. Its allocation and mapping effects are confined to the process. A
kernel-text sample and byte comparison would come later.

The mapping probe completed on the launch-model 12.70 console. `/dev/gc`
opened, one 2 MiB garlic buffer allocated and mapped at `0x200400000`, and
only VMID 6 reached a valid 2 MiB leaf for that virtual address. The VMID 6
entries were `PML4E=0x13884005`, `PDPTE=0x13895005`, and
`PDE=0x004000045b0004f7`. All other populated VMIDs stopped at an invalid
entry on that path. `munmap` and direct-memory release both returned zero.
The reported `errno=3` alongside successful `munmap` is a stale errno value
from the probe's logging; the source now emits zero on success. This confirms
the address-indexed VMID 6 mapping on this run, but not command submission or
GPU access to kernel memory.

The GPU copy probe, `gpuvm-dma-probe-1270.elf`, allocates three 2 MiB
garlic buffers (source, destination, command), verifies that their mappings
have distinct valid 2 MiB leaves in one VMID, and submits one 4 KiB GPU
buffer-to-buffer copy. It checks all 4 KiB of the destination and verifies
that the source pattern stayed intact. It does not retarget a GPU page-table
leaf or access kernel memory through the GPU. The command format is from the
13.60 reference.

The copy probe completed on 12.70. The GPU opened in VMID 6, three 2 MiB
garlic buffers mapped to distinct leaves
`0x004000045b0004f7`, `0x004000045b2004f7`, and `0x004000045b4004f7`.
The 4 KiB DMA command returned zero, destination bytes matched the intact
source at the first poll, and all three buffers unmapped and released with
zero return values. This proves ordinary buffer-to-buffer GPU DMA for this
process. It does not prove GPU access to system RAM or XOM kernel text.

The PA probe, `gpuvm-pa-preflight-1270.elf`, is read-only. It translates
the first kernel `.data` page through the current CPU page tables, compares
all 4 KiB with its direct-map physical alias, and logs the physical address,
page size, offset within a 2 MiB frame, hash, and nonzero byte count as
`GPA1270,1,` records. On the launch-model 12.70 console it resolved
`KERNEL_ADDRESS_DATA_BASE=0xffffffffce3c0000` to PA `0x0e3c0000` through a
4 KiB CPU leaf. The page's offset within its 2 MiB physical frame was
`0x1c0000`; 2876 of 4096 bytes were nonzero, and the direct-map alias
matched all 4 KiB. The page hash was `0xbdcbddf713a142f4` on that run.

The known-data probe, `gpuvm-known-data-probe-1270.elf`, recalculates that
translation and alias at runtime, then allocates three fresh garlic buffers.
It requires distinct 2 MiB GPU leaves in VMID 6 and the observed `0x4f7`
leaf flags. It changes only the source buffer's GPU PDE to the aligned
physical frame containing the verified kernel `.data` page, with bit 50 set.
It submits one 4 KiB GPU copy into a normal destination buffer, compares
against the CPU reference, restores the original PDE with readback, and
cleans up. This is the first 12.70 test that writes a GPU page-table entry;
a failure or interruption during the retargeted interval could affect the
GPU process or hang the console. Passing it would prove the GPU can read
known system RAM. It would not yet prove XOM kernel-text access.

The known-data probe passed on the launch-model 12.70 console. It retargeted
VMID 6 PDE at PA `0x13885018` from `0x004000045b0004f7` to
`0x004400000e2004f7`. The GPU copied 4 KiB from the kernel data page and
matched the CPU reference at poll 0. The original PDE restored on the first
attempt and all three buffers cleaned up successfully. This confirms the
bit-50 GPU read of known system RAM on 12.70.

The next staged probe, `gpuvm-xotext-probe-1270.elf`, translates the first
kernel `.text` page without reading its bytes on the CPU. It requires a CPU
execute-only, executable leaf, then uses the same fresh VMID 6 GPU source
leaf to read one 4 KiB page. It restores the GPU PDE, logs a hash, first
eight bytes, and byte counts, and writes the 4 KiB sample to
`/mnt/usb0/PS5-12.70-ktext-page0.bin`. The USB file should be copied into
`/home/deep/src/ps5/testing` for offline inspection. A nonzero sample alone
will not establish that these are usable kernel instructions; the bytes
must be inspected before claiming an XOM defeat or scaling up to a dump.

That first-page probe completed without a panic: the text VA
`0xffffffffcd670000` mapped through a 4 KiB CPU leaf
`0x040000000d670101` to PA `0x0d670000`, the GPU command returned zero, and
the source PDE restored. The output was **exactly 4096 bytes of `0xff`**:
first eight bytes `ffffffffffffffff`, nonzero count 4096, `0xa5` count 0,
and FNV-1a hash `0xc0b014328067f325` (the all-`0xff` page hash). This is
not usable instruction text. One page cannot distinguish intentional filler
from a GPU read restriction or a translation issue, so a full dump is not
justified yet.

`gpuvm-xotext-pivot-probe-1270.elf` uses the same bounded GPU read on text
offset `0x2A8000`, the 4 KiB page containing the candidate pivot gadget at
`0x2A815E`. The prior 12.70 page walk found this region as a 2 MiB
execute-only text mapping. Its output is
`/mnt/usb0/PS5-12.70-ktext-pivot-2a8000.bin`. A code-bearing page would
distinguish first-page filler from a broader read failure and could provide
the first independently inspectable candidate gadget bytes.

The pivot-page probe also completed its GPU transfer, restored its PDE, and
cleaned up, but the sample was again **exactly 4096 bytes of `0xff`** (FNV-1a
`0xc0b014328067f325`). This time the VA was `0xffffffffcd918000`, the PA
was `0x0d918000`, and the CPU leaf was the 2 MiB execute-only PDE
`0x040000000d8001a1`. Thus two text pages with different CPU leaf sizes
returned the same unusable data. The `end,ok` line describes the DMA and
cleanup path; it does not indicate recovered code.

`gpuvm-xotext-db-probe-1270.elf` is the last bounded discriminator for this
GPU read path. It reads the live IDT's vector 1 (`#DB`) gate, validates its
selector/type/present bits and that its handler lies in the 12.70 kernel text
range, then targets the 4 KiB page containing that handler. Because the CPU
executes that handler, an all-`0xff` sample cannot reasonably be dismissed as
an unused or filler text page. The probe uses the previously exercised one-page
DMA, restores the GPU PDE, and writes
`/mnt/usb0/PS5-12.70-ktext-db-handler.bin`. Its final log now distinguishes
`content=all_ff` from `content=varied`. If this third text sample is also all
`0xff`, stop scaling this GPU method into a dump and investigate the read
restriction or a different acquisition path. Even `content=varied` requires
offline disassembly at the reported handler offset before accepting the bytes
as plaintext instructions.

The `#DB` handler probe ran on the 12.70 launch-model console. The live gate
pointed to `0xffffffffcd988730`, so the target was the 4 KiB page at
`0xffffffffcd988000` (PA `0x0d988000`, CPU leaf
`0x040000000d8001a1`). The GPU command returned 0; the destination changed
and was stable at poll 0; the original GPU PDE was restored and verified on
the first attempt; all three buffers cleaned up. Yet the sample was **4096
bytes of `0xff`**, hash `0xc0b014328067f325`, and the final line reported
`end,ok,content=all_ff`. Because the target is a live exception-handler page,
the `0xff` result cannot be treated as recovered executable bytes or as
plausible unused-page padding. The tested GPU retarget/DMA route can read
known 12.70 kernel data, but it has not read plaintext XOTEXT. Stop GPU text
dump attempts with this mapping recipe. The precise reason for the `0xff`
readback remains unproved; it could be a device-side protection or a missing
translation/cache detail. The saved 4 KiB USB file is not needed for
disassembly unless its contents differ from the logged byte counts.

[Byepervisor-Reborn issue #5](https://github.com/PS5Dev/Byepervisor-Reborn/issues/5)
reports a 12.40 port attempt. Its `kernel_pmap_store`, IDT, COMMON_TSS, and
direct-map-global *data-relative* offsets match our measured 12.70 values
**exactly**: `+0x2E1CFB8`, `+0x2E88300`, `+0x2E8AFE0`, and pmap-relative
`+0x29C/+0x2A0/-0x11AC`. This is useful evidence of a stable data layout
from 12.40 to 12.70, rather than proof that the whole firmware family shares
one offset table.
It does not provide a 12.70 text dump or verify 12.70 gadgets. Its proposed
12.40 `SYS_GETUID` text offset differs from our 12.70 candidate, so text
offsets should not be transferred between those firmwares without bytes.
The issue's `AcpiGbl_FACS` location at kdata+`0x2CB4C80` was checked and
confirmed on 12.70 below. The older PS5 Linux
loader's FACS-corruption route installs a `#GP` handler and IST stack backed
by a kernel ROP chain before changing that pointer. It therefore does not
avoid the need for valid executable gadget addresses on 12.70.

`facs-preflight-1270.elf` performs that bounded check. It reads the candidate
global at kdata+`0x2CB4C80` and the adjacent ACPICA layout suggested by the
13.60 live result: FADT window beginning at `-0x170`, DSDT pointer at `-0x30`, and
original DSDT header at `-0x28`. It derives DMAP from the already validated
pmap fields and reports whether the FADT's `FIRMWARE_CTRL` physical address
maps exactly to the candidate FACS pointer; the DSDT relationship is logged
as an independent cross-check. It does **not** follow either pointer, alter
kernel memory or page tables, install a handler, or request rest mode. A
`candidate_match=1` validates this data offset, not the FACS-trigger exploit
or the missing executable gadgets.

The first FACS preflight returned `candidate_match=0`, but its logs expose a
more specific result: the candidate qword was `DMAP+0x7fd6e000`, the adjacent
DSDT qword was `DMAP+0x7fd89000`, and the original DSDT header began with
`DSDT`. Those two physical addresses match the independent 13.60 ACPICA
observation. The initial FADT check assumed the `FACP` header began exactly
`0x170` bytes before the candidate; the logged `0x00000003` and following
bytes imply the header is shifted inside that small window (likely +5 bytes).
The probe now scans the first `0x10` bytes of the same read-only FADT window
for `FACP` and interprets its fields relative to that signature. The first
`candidate_match=0` therefore must not be read as evidence that the 12.40
FACS offset is wrong on 12.70; the candidate itself has strong structural
support. The corrected cross-check is reported next.

The corrected FACS preflight passed on the 12.70 launch model. It found
`FACP` at window offset `5`, length `276`, with
`FIRMWARE_CTRL=0x7fd6e000` and `X_FIRMWARE_CTRL=0`.
`AcpiGbl_FACS` at kdata+`0x2CB4C80` contained
`DMAP+0x7fd6e000`; the adjacent DSDT pointer contained
`DMAP+0x7fd89000`, matching the FADT's DSDT physical address, and its
copied header began with `DSDT`. Both cross-checks returned 1, so the
**12.70 FACS global address is now verified**. The probe did not modify it.

This removes one data-offset uncertainty for an alternative `#GP` resume
trigger. It does not establish that the old FACS-corruption flow executes
correctly on 12.70: the older Linux loader installs a new IDT/IST handler
and runs a firmware-specific ROP chain before changing the pointer. The
12.70 chain's gadget bytes and effects remain unverified, and two candidates
from the unpushed ELF mapped to NX pages. Do not arm the FACS trigger on the
current evidence. The next work is an offline inventory of independently
supported 12.70 executable addresses and a chain review; only then would a
bounded console test be justified.

## October 13 source audit and next bounded check

EchoStretch's public kstuff-lite `prosper0gdb/offsets/12_40.h` and `12_70.h`
have 74 identical `DEF` entries out of 78; the four changes are `malloc`,
`loadSelfSegment_watchpoint`, and the two PPR index helpers. That supports
reusing the public 12.70 instruction anchors, while the unpushed ELF's
Byepervisor ROP table still needs independent validation. In particular,
the public 12.70 `doreti_iret`, `rep_movsb_pop_rbp_ret`, and
`store_rax_rdi` convert to text offsets `0x2B34AD`, `0x2EFC3A`, and
`0x2ABF92` using the observed `0xD50000` text/data gap. These are useful
anchors, but their instruction sequences are not drop-in replacements for
the current `POP_RDI` and `CLD` ROP slots.

`gadget-page-probe-1270.elf` now walks the mappings for all 21 candidate
ROP entries, the three relevant kernel symbol addresses, and those three
public anchors (27 total). It makes no kernel writes and never executes a
candidate gadget. `GPG1270,1,page` lines report effective NX and leaf size;
`GPG1270,1,end` gives the NX count. The earlier seven-target run confirmed
`POP_RDI` and `CLD` are NX. The expanded run completed on the 12.70 launch
model with `nx_targets=2,total=27`. All 19 other candidate gadgets, the
three candidate symbol addresses, and the three public anchors mapped with
NX clear and XOTEXT set. `POP_RDI` mapped to an NX 4 KiB data page at
`0xffffffffce3d5548`; `CLD` mapped to an NX 2 MiB data leaf at
`0xffffffffce896933`. This excludes additional NX entries in the tested
table, but executable mapping alone cannot verify gadget bytes or the
resume-call instruction. The live hook remains disabled.

The new pLinux5-NG source sketches the subsequent Linux handoff on top of
Byepervisor's S3 hook. Its `PORTING.md` describes a 13.20 high-firmware
vector and explicitly says the staged headless boot has not run on hardware.
It contains no 12.70 offset table, so it does not remove this port's hook
and gadget blockers. Its `source/utils.c:set_offsets()` handles only 13.20 in
the high-firmware range. Its vendored `find_pte()` still descends through a
2 MiB PDE leaf, and `escape_kernel_text()` calls that walker for every text
page. The 12.70 console's text mapping has six such 2 MiB leaves, so that
path needs the same large-page correction already made in this fork before a
12.70 Linux attempt.

## Prepared carrier and hook checks (not run on hardware)

Sonic's S3 AP-launch writeup says the physical `0x3ffff000` carrier is
populated before suspend and survives S3. The old diagnostic instead tried
to copy its image with a ROP `memcpy` after the resume breakpoint. That path
requires both the invalid `CLD` and `POP_RDI` slots.

`carrier-read-probe-1270.elf` reads the 4 KiB carrier through the existing
direct map and logs `CARR1270,1,page` with its hash, zero/`0xff` counts, and
edge qwords. It does not write memory or arm a hook. Run this first. The
prepared diagnostic below requires the entire carrier page to be zero and
stops before writing if that check fails.

The first live carrier read completed cleanly, but the page was not zero:
`zero=2579`, `ff=46`, and FNV-1a hash `0x4b0842504dbaead8`. The untested
prestage diagnostic would therefore stop at its guard. Its guard must not be
removed on this evidence. `carrier-layout-probe-1270.elf` is the next
read-only check: it logs sixteen 256-byte chunk summaries and compares a
second full-page read after five seconds. Stability would help identify the
contents but would not prove that overwriting them is safe.

The layout probe completed on hardware. Its whole-page hash was again
`0x4b0842504dbaead8`, and the second read five seconds later had
`changed=0`. Fourteen of sixteen 256-byte chunks contained nonzero data;
only the chunks at `0x100` and `0x900` were entirely zero. The final
`0xF00` parameter area had 146 nonzero bytes. This rules out treating the
page as empty scratch. The remaining bytes could be static or idle system
data; two snapshots do not establish ownership or that overwriting them is
safe. Keep the prestage diagnostic's zero-page guard in place. The next
design task is to identify an owned physical page that is executable under
root 0 and survives S3, or an equivalent staging method that preserves the
existing carrier contents.

`owned-carrier-probe-1270.elf` tests whether the normal direct-memory
allocator will grant a 4 KiB or 2 MiB type-0 allocation with a requested
range below `0x40000000`, then releases it immediately. It performs no
kernel page-table writes or hook installation. An allocation result is only
a candidate: the returned offset still needs physical-address translation,
root-0 execute permission, S3 retention, and safe AP use verified before
changing the diagnostic.

The allocator probe completed: its 4 KiB type-0 request returned
`0x80020016`; a 2 MiB request succeeded with offset `0x201f200000` and
released cleanly. That offset is an allocator value, not a verified machine
physical address. `owned-carrier-map-probe-1270.elf` now requests the same
2 MiB block, maps it, walks the current process page tables to translate the
first page, checks a marker through the direct-map alias only below the
16 GiB read cap, and unmaps/releases the block. It touches only memory
owned by that allocation and does not install a hook.

`byepervisor_1270_prestage_diag.elf` is a separate, **untested** target. It
places the 177-byte diagnostic AP image and six parameters on the carrier
before arming; reads them back; changes only the carrier PML4 NX bit; and
builds an empty handler chain. Its `#DB` arm trigger puts the resumectx
pointer in `RDI` directly. The continuation uses `POP_RCX`, `POP_R8`, and
`STORE_RCX_R8` to write the IST slot. The dispatch tail leaves the
interrupted `RDI` alone. No ROP slot in this variant references the two NX
candidate addresses. The old diagnostic target retains its refusal to run
on 12.70.

Successful compilation and executable page mappings do not verify the
remaining gadget instructions, the breakpoint location, carrier retention,
or the AP callback contract. The new target can still panic the console.
The carrier probe did not report a zero page, so this diagnostic is not ready
for a hook test. It needs an operator present to enter rest mode and recover
from a panic after the carrier issue is resolved. The full HV-modifying
payload remains disabled on 12.70.
